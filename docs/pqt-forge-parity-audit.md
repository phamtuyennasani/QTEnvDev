## Shell settings operation contract

The Forge shell reads the existing saved appearance and startup settings. Appearance follows the operating system when set to System. Window hiding is a one-way command after renderer initialization. The tray bridge owns state publication and accepts one command at a time. It delegates execution to the existing startup group runner or service owner. Automatic startup waits for the data directory and starts the visible default group once in the background. When a default group is unavailable, it only attempts visible, enabled services whose availability has been verified. Failures in discovery affect the service they belong to. Window hiding and group launch are independent. The Electron fixture exercises preference updates, boot, tray command order and partial discovery.

## Homebrew operation contract

- Package Library owns source selection, search and confirmation. The renderer-lifetime Homebrew panel controller owns its read model, catalog loading, tap setup and notices for failures before submission. The existing `homebrewUpgrade` singleton owns Homebrew install, uninstall and the PHP upgrade preview and execution. There are no new stores, shared configuration fields or lifecycle exceptions.
- Opening a supported Homebrew source requests its module's `brewinfo`. One load per module can run at a time. PHP upgrade eligibility is a supplementary lookup. Results from unrelated package sources do not replace Homebrew results.
- Package and tap actions capture the target before dispatch. Progress (`code: 200`) keeps the listener alive. Terminal outcomes release listeners, while an unknown mutation blocks replay. Closing and reopening the library leaves the operation and its result in the controller.
- The existing Homebrew main coordinator and fork runner own mutation admission and child processes. Install and uninstall use their existing service checks. PHP upgrade uses the existing approved service stop targets and `ModuleInstalledItem.stop()`. Native Homebrew formulae never go through the application's managed directory deletion.
- Discovery and admission are required for their dependent actions. A tap failure does not remove usable formulae from other sources. After confirmed mutation success, refreshing catalogs and notifying the UI are supplementary. Refresh failure preserves terminal success with a warning.
- Verify provider and platform gating, selected source routing, progress, duplicate prevention, mutation outcomes, refresh failure, and closing and reopening the dialog. Use the existing Homebrew controller and service lifecycle tests for the shared execution path. Live macOS execution remains a separate acceptance check.

The Homebrew bootstrap singleton owns PTY launch, output, cancellation and terminal cleanup. Closing Package Library retains the operation. A process exit is required before discovery. Rediscovery can be retried independently after a successful install. The macOS build unpacks the installer scripts for the system shell. The Homebrew Electron fixture tests failures and retry.

The Runtimes panel selects a PHP binary before opening the extension drawer. The existing provider controllers own discovery, writes, progress, duplicate guards and terminal cleanup. Loaded extension discovery, extension directory discovery and provider search are independent. Verify the normal Runtimes entry point and platform/source gating using fixture IPC.

## Corrections from the Phase 0 and 1 review

The existing Tomcat renderer singleton retains ownership of site saving. The fork write is required. The subsequent UI refresh, OS hosts sync, and restart of a previously running Tomcat are independent. They finish with individual warnings if they fail, while the committed record stays saved. The operation retains its duplicate guard through restart and uses the existing service lifecycle. Test failure of each follow-up, including a false restart response. Editing a Tomcat record must round-trip fields outside the form.

The Websites screen uses the same Tomcat transaction for removal as for add and edit. The dialog owns confirmation and unsaved form inputs, including the rewrite and candidate mappings. The website controller holds the list mutation until the Tomcat operation returns. The fork owns the host file and Catalina configuration transaction. A read failure before the write must preserve the original host file. Optional App Base discovery preserves the root and existing mappings on failure. Verify Tomcat routing, guard through startup and restart, write failure, and independent follow-ups. No store or shared configuration exception is needed.

The existing PHP Projects controller retains its renderer-lifetime start/stop guard. Commands still use the underlying project lifecycle and its terminal result. A false result stays false. The Overview change is display-only and counts reported running services without deriving health from those counts.

The Websites language project manager opens the established project list and scaffolding views. The mounted panel owns the selected language and tab. The existing ProjectSetup and scaffolding workflows own saved projects, long-running commands, progress, duplicate guards and cleanup. The overview reads from those same project instances, including the legacy `node` storage key. Project discovery runs separately for each language, so one failed read can leave the others usable. The renderer fixture should check the normal entry point, projects stored before the migration and access to both views. No store, lifecycle or persistence exception is needed.

The service file controller keeps the requested version and path for each read or write. The PHP INI dialog uses the fork module's resolved path. Older reads cannot replace a newer selection or a closed dialog. Test delayed reads and an external change before Save. Reading a log is independent of editing a config.

Website files use a separate instance of the service file editor controller. The website adapter reports file paths and owns the restart policy after a file write. The dialog owns the selected website and the log clear confirmation. It gives the controller an immutable file scope and drops obsolete previews on close. A completed config write remains complete when its affected server cannot restart. Tomcat's generated files are read-only here and managed through the dedicated editor. Exercise stale reads, external edit detection and post-write failure. No new store or persistence policy is needed.

The Websites controller also serializes saved ordering with site mutations. The fork reads the current host file, checks the order shown when the user acted, then saves only the new order and pin flag. Ordering does not generate vhosts, sync system hosts or restart services. A missing terminal result disables another write until verification. Test moving within each pin group and a stale order.

The Websites controller also owns the request and result for creating sites from subdirectories. It keeps the write guard until the fork returns and until any post-save synchronization finishes. The fork scans immediate directories, skips invalid or conflicting hostnames, and generates each site's files separately. A child failure does not stop other children. When this is requested from the editor, the parent save remains required and the child scan is supplementary. System hosts sync and server reloads run only after a committed change. The UI owns only the confirmation and the form checkbox. Test filtering, child failure, a stale parent, and a successful save with sync warnings. No module boundary exceptions are needed.

The Websites host controls reuse HostsSettingsController for automatic system hosts updates and IPv6. The controller keeps the current options while it waits for the fork's terminal result and rejects duplicate submissions. The Websites mutation guard prevents overlap with site changes. Applying the operating system change is required. Remembering preferences is supplementary. Copy and reveal use the existing generated preview file, and manual editing opens the established platform editor. These actions do not manage a service process. Test navigation and normal entry points with isolated IPC.

The HTTPS editors expose the local CA file and the platform command for manually trusting it. The website module keeps copy and reveal feedback across navigation and prevents overlap. Both actions require the generated public certificate. The command is sent to the clipboard, and neither action starts a process or changes system trust. Verify the website entry, the exact public certificate path, and a missing certificate.

The backup format stores site records and vhost and rewrite files together. Import also reads the legacy JSON list with its adjacent config files. Users review the sites before importing. Import adds records and rejects conflicts with saved sites or files. Backups exclude source code, logs and TLS keys. When TLS material is missing the preview reports which sites will be imported with HTTP. See the [backup and queue contract](../src/fork/module/Host/WebsiteBackupContract.md).

Cron keeps per-task or per-draft outcomes for the renderer lifetime. The shared portable schedule validator runs before submission. The fork owns scheduling and process execution. The controller retains the command exit code and output independently of list refresh. While a mutation is awaiting a terminal response, another cannot begin. A timeout leaves the result unknown and blocks replay of that operation. Verify validation, progress, command failure and refresh failure independently.

The Websites task link carries the selected host into Scheduled tasks. The destination starts with that website selected for filtering and creation. The task controller still loads the full list and owns mutations, so the user can clear the filter and pending results survive navigation.

Scheduled Tasks uses the same renderer singleton for run history and the system scheduler. The mounted view owns filter and confirmation selection. History requests retain their task identity through navigation and use a bounded record count. System scheduler deletion requires confirmation of a row from the latest successful list. The singleton serializes deletion with app-managed task mutations, treats missing terminal results as unknown, and keeps committed removals when either list refresh fails. The fork owns the exact OS scheduler target and local metadata. Verify history isolation, failure and retry, a stale selection, and preservation of confirmed deletion after a failed refresh.

The task editor also lets the user run the current command before saving it. The singleton retains the command and working-directory snapshot until the fork returns its exit code and output. An editor instance displays only its own result. The controller prevents overlap with scheduler mutations and reports completion after navigation. A missing terminal result blocks repeated execution in this renderer session. This action never writes a task, a run-history entry, or an OS scheduler registration. Verify duplicate clicks, directory and command capture, nonzero exit and unknown results.

For database access, the existing MySQL state owns saved credentials and one hydration flight. The next database tools controller awaits hydration before querying lists. A stale read cannot update the selected database's details. Password changes retain their existing backend, guard and terminal result. The controller captures the selected database and version before submitting a change. Connection values that are not reported by the selected module remain unknown.

The MariaDB fork chooses its dump program beside the selected server binary. Older installations may ship only the former `mysqldump` name. Executable discovery is required for each backup request. Each selected database gets its own result, and a completed dump remains available when another database fails. The Windows native fixture exercises connection, database creation, account login, discovery and the saved SQL dump on an isolated loopback instance.

Tomcat and PostgreSQL file listings use the stored directory for the selected version. The service file controller owns the request and selected file preview. The adapter reuses each module's directory resolver, and the fork reports the files under that directory. Failure to resolve or list files leaves the dialog in an error state without changing service state or restarting anything.
