# Flutter in Runtimes

The established Flutter fork owns SDK discovery, diagnostics, ADB, Flutter and Dart processes, and file writes. Renderer controllers live with the Flutter module and share both entry points. Views own selected folders, tabs, dialogs and form drafts. The SDK, doctor and Android reads coalesce by method. These reads can refresh independently. A failed read keeps the previous successful result.

Flutter commands snapshot the action, directory and setup. One command can run at a time. Android environment repairs and device changes retain their own operation state. Flutter project create and save snapshot the selected SDK and payload and share one write owner. The owner retains progress until a terminal reply, notices after a view closes, and listener cleanup. A confirmed write stays completed when updating the saved project entry or its environment fails. An unconfirmed write remains visible and prevents replay. No new store, persistence format, or process lifecycle is introduced.

Verify the Flutter entry through Runtimes, shared diagnostic reads, a command that finishes after switching tabs, and the existing saved project and create/edit controls.
